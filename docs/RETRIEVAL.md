# Retrieval

## 1. Назначение

Retrieval — слой семантического поиска EgoBiz Wiki.

Его задача — найти наиболее релевантные фрагменты из проиндексированной корпоративной базы знаний по запросу пользователя.

Retrieval является промежуточным этапом между пользовательским запросом и последующим RAG-процессом.

На данном этапе Retrieval:

* принимает текстовый запрос;
* преобразует запрос в embedding;
* выполняет поиск похожих векторов;
* получает наиболее близкие фрагменты базы знаний;
* сохраняет metadata и информацию об источнике;
* возвращает результаты в порядке релевантности.

Retrieval не генерирует итоговый ответ пользователю и не отвечает за генерацию текста с помощью LLM.

## 2. Поток Retrieval

```text
Запрос пользователя
        ↓
Проверка запроса
        ↓
Embedding запроса
        ↓
Поиск похожих векторов в ChromaDB
        ↓
Top-K результатов
        ↓
Необязательная фильтрация по distance
        ↓
Сортировка результатов
        ↓
RetrievedChunk
```

## 3. Архитектурное расположение

Retrieval реализован с разделением на domain, application и infrastructure layers.

```text
app/
├── domain/
│   └── retrieval.py
│
├── application/
│   └── retrieval/
│       └── service.py
│
└── infrastructure/
    ├── embeddings/
    │   └── openai.py
    │
    └── vector_store/
        └── chroma.py
```

Такое разделение позволяет application layer работать через абстракции и не зависеть непосредственно от ChromaDB или конкретного embedding-провайдера.

## 4. Domain Layer

### RetrievedChunk

Файл:

`app/domain/retrieval.py`

Результат Retrieval представлен доменной моделью `RetrievedChunk`.

Модель содержит:

* `chunk_id` — идентификатор найденного фрагмента;
* `document_id` — идентификатор исходного документа;
* `content` — текст найденного фрагмента;
* `distance` — расстояние до поискового запроса;
* `metadata` — metadata исходного документа;
* `source` — человекочитаемый источник.

Модель является частью domain layer и не содержит зависимости от ChromaDB.

Это позволяет использовать результат Retrieval на последующих этапах приложения независимо от конкретного vector store.

## 5. Application Layer

### RetrievalService

Файл:

`app/application/retrieval/service.py`

`RetrievalService` является application-level сервисом, координирующим процесс семантического поиска.

Основные обязанности сервиса:

1. проверить пользовательский запрос;
2. удалить начальные и конечные пробелы;
3. получить embedding запроса;
4. передать embedding в vector store;
5. запросить заданное количество результатов;
6. при необходимости применить distance threshold;
7. отсортировать результаты;
8. вернуть список `RetrievedChunk`.

Application service не зависит непосредственно от ChromaDB.

## 6. QueryEmbeddingProvider

`QueryEmbeddingProvider` — application-level Protocol для получения embedding пользовательского запроса.

Application layer использует только необходимый контракт:

```python
embed_query(query: str) -> list[float]
```

Конкретная реализация находится в infrastructure layer.

В текущем MVP используется `OpenAIEmbeddingProvider`.

Для query embedding используется та же embedding-модель, которая применяется при индексации документов.

Это необходимо для того, чтобы embeddings документов и пользовательских запросов находились в одном векторном пространстве.

## 7. RetrievalVectorStore

`RetrievalVectorStore` — application-level Protocol для выполнения векторного поиска.

Application layer не знает, каким именно vector database или библиотекой выполняется поиск.

Текущая реализация:

`ChromaVectorStore`

Основной контракт:

```python
query(
    embedding: Sequence[float],
    n_results: int,
) -> list[RetrievedChunk]
```

Это позволяет в дальнейшем заменить инфраструктурную реализацию без изменения `RetrievalService`.

## 8. Infrastructure Layer

### ChromaVectorStore

Файл:

`app/infrastructure/vector_store/chroma.py`

`ChromaVectorStore` является infrastructure adapter для работы с локальной коллекцией ChromaDB.

Для Retrieval он:

* принимает embedding поискового запроса;
* выполняет similarity search;
* получает документы из коллекции;
* получает metadata;
* получает distance;
* преобразует результат ChromaDB в `RetrievedChunk`.

Application layer при этом не работает непосредственно с объектами ChromaDB.

## 9. Query Embedding

Для каждого пользовательского запроса выполняется embedding.

Пример:

```text
"Как подключиться к VPN?"
        ↓
Query Embedding
        ↓
Вектор запроса
        ↓
ChromaDB similarity search
```

Важное архитектурное правило MVP:

**embedding-модель для индексации документов и embedding-модель для пользовательских запросов должна быть одной и той же.**

Это обеспечивает сопоставимость векторов документов и запросов.

## 10. Top-K

Количество возвращаемых результатов задаётся параметром:

```text
RETRIEVAL_TOP_K
```

Значение по умолчанию:

```text
5
```

Таким образом, Retrieval по умолчанию запрашивает не более пяти наиболее близких фрагментов.

Top-K является конфигурационным параметром, поэтому его можно изменить без изменения application logic.

## 11. Distance Threshold

Дополнительно поддерживается параметр:

```text
RETRIEVAL_SCORE_THRESHOLD
```

Он является необязательным.

В текущей реализации значение интерпретируется как максимальное допустимое расстояние ChromaDB.

Правило:

```text
distance <= threshold
```

Результаты с большим `distance` исключаются.

Параметр не задан по умолчанию.

Это позволяет сначала наблюдать реальные значения distance на базе знаний, а затем при необходимости подобрать рабочий threshold.

## 12. Интерпретация Distance

Для используемого Retrieval:

```text
меньший distance → большая близость
больший distance  → меньшая близость
```

Поэтому результаты сортируются по возрастанию `distance`.

Пример:

```text
0.68
0.91
1.17
1.42
```

В таком случае результат с `0.68` считается более близким к запросу, чем результат с `1.42`.

Важно: конкретное значение distance не следует интерпретировать как универсальный процент релевантности.

Порог релевантности должен определяться на основании реальных данных и результатов evaluation.

## 13. Валидация запроса

Пустой запрос не передаётся в embedding provider.

Следующие значения считаются некорректными:

```text
""
"   "
```

Перед обработкой начальные и конечные пробелы удаляются.

Например:

```text
"  Как оформить отпуск?  "
```

преобразуется в:

```text
"Как оформить отпуск?"
```

## 14. Порядок результатов

Retrieval возвращает результаты в порядке возрастания `distance`.

То есть:

```text
лучший результат
      ↓
меньший distance
      ↓
...
      ↓
худший результат
      ↓
больший distance
```

Это обеспечивает предсказуемый порядок контекста для последующего RAG-слоя.

## 15. Metadata и Source

При Retrieval сохраняется metadata исходного документа.

В результате доступны, в частности:

* `document_id`;
* путь к документу;
* название документа;
* категория;
* подкатегория;
* источник;
* версия;
* язык;
* уровень доступа;
* дата обновления.

Также сохраняется поле `source`.

Это необходимо для последующего отображения пользователю источников, использованных при формировании ответа.

## 16. Пустая база знаний

Если коллекция ChromaDB не содержит документов, Retrieval возвращает:

```python
[]
```

Исключение при этом не возникает.

Такое поведение позволяет последующим слоям приложения корректно обработать отсутствие доступного контекста.

## 17. Запросы вне базы знаний

Retrieval сам по себе не формирует итоговый fallback-ответ пользователю.

Если пользователь задаёт вопрос, информации о котором нет в базе знаний, vector search всё равно может вернуть ближайшие по векторному расстоянию документы.

Поэтому само наличие результатов Retrieval ещё не означает, что найденный контекст является достаточным для достоверного ответа.

На следующем этапе RAG/application layer результаты Retrieval и критерий релевантности будут использоваться для принятия решения о возможности формирования ответа.

Требуемый fallback-ответ MVP:

> В базе знаний не найдено достаточно информации для достоверного ответа на этот вопрос.

## 18. Пример ожидаемого поведения

Для запроса:

```text
Как подключиться к VPN?
```

ожидается, что среди первых результатов будет документ:

```text
IT / Корпоративный VPN
```

Для запроса:

```text
Как оформить отпуск?
```

ожидается документ:

```text
HR / Политика отпусков
```

Для запроса:

```text
Что делать при фишинговом письме?
```

ожидается документ:

```text
Security / Фишинг
```

Для вопроса, не относящегося к предметной области базы знаний, например:

```text
Как заказать домик на Марсе?
```

не должен автоматически считаться достаточным любой случайно найденный документ.

Окончательное решение о достаточности контекста относится к последующему RAG/application layer.

Эти возможности относятся к следующим этапам разработки.

## 23. Почему не используется усложнённый Retrieval

Для MVP не используются дополнительные механизмы поиска без подтверждённой необходимости.

В частности, на данном этапе не добавляются:

* hybrid search;
* BM25;
* reranking models;
* query expansion;
* multi-query retrieval;
* agentic retrieval.

Причина — текущая задача проекта состоит в создании простого, полного и работающего MVP.

Дополнительные механизмы могут быть добавлены позже, если результаты evaluation покажут недостаточное качество базового semantic retrieval.

## 24. Архитектурное решение

Для MVP выбран классический semantic retrieval через ChromaDB.

Архитектура намеренно разделяет:

```text
Domain
  ↓
Application
  ↓
Infrastructure
```

При этом application layer работает через Protocols, а конкретная реализация vector store находится в infrastructure layer.

Такой подход обеспечивает достаточную расширяемость без преждевременного усложнения проекта.

Главный принцип разработки EgoBiz Wiki:

**SIMPLE, COMPLETE & WORKING MVP > COMPLEX, UNSTABLE PRODUCT**

Поэтому текущая реализация Retrieval считается достаточной для перехода к следующему этапу — построению RAG pipeline.
