# Evaluation Dataset

## Назначение

**Evaluation Dataset** — формальный набор тестовых кейсов для проверки качества MVP EgoBiz Wiki.

Набор используется для объективной оценки уже реализованного RAG-пайплайна до добавления дополнительных механизмов поиска или усложнения архитектуры.

### Основные цели

* Проверить качество retrieval.
* Проверить корректность RAG-ответов.
* Проверить работу fallback.
* Проверить корректность указания источников.
* Проверить поведение системы на типичных вопросах сотрудников.
* Выявить ограничения текущего MVP и определить дальнейшие улучшения.

---

## Объём

Evaluation Dataset содержит **38 тестовых кейсов**.

Набор обеспечивает покрытие всех 23 документов текущей корпоративной базы знаний и включает вопросы различных типов, в том числе вопросы, на которые система не должна давать содержательный ответ.

Уникальные идентификаторы кейсов: `eval-001` — `eval-038`.

---

## Категории тестов

* **Relevant — 14 cases**

  Вопросы, для которых в базе знаний имеется достаточная информация.

  *Проверяется:* наличие релевантного контекста, корректность ответа, соответствие ответа информации из базы знаний, корректность источников.

* **Cross-category — 8 cases**

  Вопросы из разных категорий базы знаний.

  *Проверяется:* retrieval и RAG работают не только для одной тематической области, но и для различных разделов корпоративной базы.

* **Typical user — 4 cases**

  Реалистичные вопросы сотрудника, сформулированные естественным языком.

  *Проверяется:* отражение реальных сценариев использования корпоративного ассистента.

* **Source attribution — 4 cases**

  Вопросы, для которых особенно важно проверить корректность указанных источников.

  *Проверяется:* соответствие источников содержанию вопроса и использованному контексту.

* **Out-of-KB — 5 cases**

  Вопросы, информация для которых отсутствует в базе знаний.

  *Ожидаемое поведение:* выводится сообщение:

  *«В базе знаний не найдено достаточно информации для достоверного ответа на этот вопрос.»*

  При deterministic fallback список источников должен быть пустым.

* **Ambiguous — 3 cases**

  Потенциально неоднозначные вопросы, для которых без дополнительного контекста нельзя однозначно определить намерение пользователя.

  *Ожидаемое поведение в evaluation dataset:* система должна запросить уточнение, если это необходимо.

  **Важно:** отдельный механизм clarification в текущем MVP не реализован. Текущая Evaluation фиксирует это как проверяемое ожидаемое поведение и как известное ограничение baseline.

## Структура тестового кейса

Каждый кейс содержит следующие поля:

* `id`
* `question`
* `category`
* `expected_behavior`
* `expected_sources`
* `expected_topics`

### Описание полей

* **id** — уникальный идентификатор тестового кейса, например `eval-001`.
* **question** — вопрос пользователя, передаваемый системе.
* **category** — категория evaluation-кейса. Допустимые значения: `relevant`, `cross_category`, `source_attribution`, `out_of_kb`, `ambiguous`, `typical_user`.
* **expected_behavior** — ожидаемое поведение системы. Основные значения: `answer`, `fallback`, `clarification`.
* **expected_sources** — ожидаемые документы или источники базы знаний, которые должны быть релевантны вопросу.
* **expected_topics** — ключевые темы или факты, которые должны быть представлены в найденном контексте или ответе.

## Покрытие базы знаний

Evaluation Dataset построен таким образом, чтобы каждый из 23 документов текущей базы знаний был представлен как минимум в одном тестовом кейсе.

Это позволяет использовать набор для проверки не только отдельных функций RAG-пайплайна, но и тематического покрытия корпоративной базы.

---

## Evaluation Runner

Автоматизированная оценка реализована в:

```text
evaluation/run_evaluation.py
```

Runner использует **существующий production RAG pipeline**, а не отдельную реализацию Retrieval или RAG.

Это позволяет измерять фактическое поведение текущего MVP без создания второго механизма поиска специально для evaluation.

Запуск выполняется из корня проекта:

```powershell
python .\evaluation\run_evaluation.py
```

## Метрики

Evaluation использует четыре основные метрики:

### 1. Behavior Accuracy

Доля evaluation cases, в которых фактическое поведение системы соответствует `expected_behavior`.

Проверяются основные типы поведения:

* `answer`;
* `fallback`;
* `clarification`.

### 2. Expected Source Hit Rate

Доля source-based cases, для которых ожидаемый источник присутствует среди фактически возвращённых источников.

### 3. Source Attribution Accuracy

Доля source-based cases, для которых фактический набор источников корректно соответствует ожидаемым источникам в рамках правил evaluation.

### 4. Fallback Accuracy

Доля cases с ожидаемым `fallback`, в которых ответ корректно содержит fallback-поведение.

Для source-based метрик используются **30 cases**, содержащих `expected_sources`.

Результаты:

## Принцип оценки

Evaluation Dataset **не требует дословного совпадения** ответа LLM с заранее подготовленным текстом.

Это важно, поскольку один и тот же корректный ответ может быть сформулирован несколькими способами.

### Основное внимание уделяется

* наличию релевантного контекста;
* соответствию ответа информации из базы знаний;
* корректному поведению fallback;
* корректности источников;
* отсутствию неподтверждённых утверждений.

`expected_topics` не оцениваются простым string containment.

Простая проверка наличия отдельных строк не позволяет надёжно определить семантическую корректность ответа и поэтому не используется как самостоятельная метрика качества ответа.

---

## Fallback Evaluation

В evaluation учитывается наличие точной fallback-фразы:

```text
В базе знаний не найдено достаточно информации для достоверного ответа на этот вопрос.
```

`eval-035` показал, что модель может вернуть fallback-фразу вместе с дополнительным пояснением.

Поэтому evaluation classifier считает такой ответ fallback при наличии точной fallback-фразы, даже если ответ содержит дополнительный текст.

Это изменение относится только к evaluation logic и не изменяет production RAG contract.

## Выявленные ограничения

Текущая Evaluation выявила несколько ограничений baseline.

### Retrieval limitations

`eval-017`:

Один из ожидаемых документов не попадает в текущий Top-K при заданных параметрах Retrieval.

`eval-023`:

Один из ожидаемых документов также не попадает в текущий Top-K.

Эти случаи относятся к ограничениям текущего vector retrieval baseline.

### Ambiguous queries

`eval-036`, `eval-037`, `eval-038`:

Для этих кейсов evaluation ожидает `clarification`, однако текущий MVP возвращает `answer`.

Это отражает отсутствие отдельного механизма управления неоднозначными запросами.

---

## Принцип развития

Сначала оценивается текущий простой RAG-пайплайн.

Только после анализа результатов Evaluation принимается решение о необходимости дальнейших улучшений Retrieval или других компонентов системы.

Усложнение архитектуры должно основываться на результатах измерения, а не добавляться заранее.

Текущие результаты сами по себе не являются основанием для автоматического добавления:

* hybrid search;
* reranking;
* query expansion;
* Agentic RAG;
* отдельного clarification engine.

Главный принцип проекта:

> **Сначала измерить проблему — затем усложнять систему.**

Цель Evaluation не заключается в искусственном достижении 100% любой ценой.

---

## Ограничения MVP

В рамках текущего evaluation не используются:

* Agentic RAG / агенты / LangGraph;
* Hybrid search;
* Reranking;
* Query expansion;
* Внешний web search;
* Long-term memory;
* LLM-as-a-Judge;
* специализированные evaluation-фреймворки.

Evaluation Dataset является самостоятельным проектным артефактом и не изменяет основную архитектуру MVP.
